Deployment & Migration

1
How does destructivechanges.xml work?
▼

destructivechanges.xml is a Salesforce Metadata API file that deletes metadata components from a target org during a deployment. It shares the same XML structure as package.xml but lists components to remove rather than deploy.

  • Pre-destructive (destructiveChangesPre.xml): Deletions run before the main deployment. Use when conflicting metadata must be removed first.
  • Post-destructive (destructiveChangesPost.xml): Deletions run after. Use for cleanup once new components are safely deployed.
  • Must be included in the same ZIP package alongside an (optionally empty) package.xml.
  • Component files do not need to be present in the package — only the XML manifest entry.
Always validate with --checkonly before running a destructive deployment in production.
Metadata APIDestructive
2
Why should products be loaded after opportunities in Salesforce during migration?
▼

Opportunity Line Items (products on an opportunity) have a required parent relationship with both Opportunity and PricebookEntry. Loading order must respect these FK dependencies:

  1. Pricebooks & Products (PricebookEntry)
  2. Accounts & Contacts
  3. Opportunities (reference Accounts)
  4. Opportunity Line Items (reference Opportunities + PricebookEntries)

If you attempt to insert Opportunity Line Items before the parent Opportunity exists, the operation fails with a parent-not-found error. Salesforce enforces referential integrity at the database level.

25
Automated deployment
▼

Automated deployment uses CI/CD pipelines to push Salesforce metadata to target orgs without manual intervention. Common tools include GitHub Actions, Jenkins, Bitbucket Pipelines, and the sf CLI.

  • Source is validated (check-only) against the target, then deployed on merge or tag.
  • Apex test execution is enforced automatically — no human bypass possible.
  • Rollback is achieved by reverting the source commit and redeploying.
  • Reduces human error, enforces code review gates, and provides a full audit trail via git history.
Use sf project deploy start --dry-run in PR checks for validation feedback before merging.
CI/CDDevOps
23
Benefits of the Ant Migration Tool
▼

The Ant Migration Tool wraps the Metadata API in Apache Ant tasks for scripted deployments.

  • Scriptable & repeatable: Build files can be version-controlled and run in CI pipelines.
  • Fine-grained control: Specify exactly which components to retrieve/deploy via package.xml.
  • Destructive changes support: Easy inclusion of destructiveChanges.xml.
  • Validation mode: checkOnly=true validates without committing changes.
  • Test level control: Specify RunLocalTests, RunAllTestsInOrg, or NoTestRun.
The Ant Migration Tool is considered legacy. Salesforce recommends migrating to the sf CLI with DX source format.
LegacyMetadata API
26
Automated change tracking
▼

Automated change tracking detects which metadata has changed in an org or source directory without manual identification. Two main forms:

  • Source Tracking: Scratch orgs and Developer/Developer Pro sandboxes record every metadata change. sf project retrieve start pulls only changed components.
  • Git-based delta: Tools like sfdx-git-delta compare git commits to build a package.xml containing only changed files, dramatically speeding up deployments.
Source tracking requires Developer or Developer Pro sandboxes. Full Copy and Partial Copy sandboxes do not support source tracking.

Packages

3
Difference between managed and unmanaged packages
▼
  • Managed packages: Code is obfuscated (IP protected), have a unique namespace, support upgrades/patches, and are listed on AppExchange. Subscribers cannot edit source. Components stay locked post-install.
  • Unmanaged packages: No namespace, code is visible and editable by the subscriber, but not upgradeable. Best for open-source templates or one-time installs.
ISVAppExchange
4
Does access to Salesforce metadata need to be switched on for a managed package during testing?
▼

Yes — managed package code cannot automatically access subscriber org metadata due to namespace isolation:

  • Subscriber must grant object-level and field-level permissions to the package's permission set.
  • In a Partner Developer or Trialforce org, configure the subscriber environment so the package can interact with pre-installed metadata.
  • For Apex tests inside the managed package, SeeAllData=false is the default — test data must be created explicitly.
ISVTesting
10 / 33
Unlocked packages
▼

Unlocked packages are the modern Salesforce DX packaging model for internal org development (not AppExchange ISV).

  • Versioned & upgradeable: Each release is a numbered version that can be installed and promoted.
  • Editable post-install: Unlike managed packages, subscribers can modify components.
  • No namespace required (optional namespaced unlocked packages exist).
  • Modular: Break large orgs into multiple packages with defined dependency chains.
  • CI/CD native: sf package version create integrates directly with pipelines.
Unlocked packages are the recommended path for the Package Development Model in enterprise orgs.

Sandboxes & Environments

6
What are preview and non-preview instances in Salesforce?
▼
  • Preview instances: Receive the upcoming major release 4–6 weeks early. Ideal for testing customizations before they reach production.
  • Non-preview instances: Stay on the current production release until GA. All production orgs run on non-preview instances.

Check your sandbox's instance in Setup → Sandboxes. Instance names indicate preview vs. non-preview status per the Sandbox Preview Guide published each release cycle.

SandboxRelease
7
What is the release preview window?
▼

The release preview window is the 4–6 week period before general availability during which preview sandboxes receive the upcoming Salesforce release. Teams use this window to:

  • Test existing customizations and integrations against the new platform version.
  • Validate that automated test suites still pass.
  • Review new features and configure Critical Update opt-in/opt-out settings.

Exact dates are published in the Sandbox Preview Guide on the Salesforce Help portal each cycle.

ReleasePlanning
8
In which sandbox should you do UAT?
▼

UAT should be conducted in a Full Copy sandbox, or a Partial Copy if Full Copy isn't available:

  • Full Copy: Replicates production data volume and structure, giving realistic performance. Business users test against familiar data. Edge cases from real data surface that synthetic data would miss.
  • Partial Copy: Acceptable when Full Copy isn't licensed — use a representative data subset.
  • Developer sandboxes are not suitable for UAT due to lack of production data fidelity.
SandboxUAT
21
Which sandbox is best for a hotfix environment?
▼

A Developer Pro sandbox or Partial Copy sandbox is typically best, balancing speed of refresh with sufficient metadata fidelity:

  • Developer Pro: Fast to create/refresh, holds more data than a plain Developer sandbox, suitable for reproducing the bug and developing the fix quickly.
  • Partial Copy: Better data fidelity for testing the fix against realistic scenarios.

The hotfix sandbox should always be refreshed from production (or a recent snapshot) so it exactly matches the metadata state where the bug exists.

24
Sandbox preview guide
▼

Salesforce publishes a Sandbox Preview Guide before each major release containing:

  • List of sandbox instances receiving the preview release and their go-live dates.
  • Instructions for opting sandboxes in or out of preview (via refresh timing).
  • Dates for preview start, freeze window, and general availability.
  • Links to Release Notes for new features.

Find it by searching "Sandbox Preview Guide [Season Year]" in Salesforce Help.

34
Drawbacks of having 2 Full Copy sandboxes
▼
  • Cost: Full Copy sandboxes are the most expensive type — two doubles licensing costs.
  • Storage: Each mirrors production data. Two sandboxes double storage consumption and fees.
  • Refresh time: Full Copy refreshes can take hours or days. Two sandboxes means double the maintenance overhead.
  • 29-day restriction: Full Copy can only be refreshed every 29 days, making it hard to keep two in sync with production simultaneously.
  • Data drift: Both sandboxes diverge from production between refreshes, reducing test reliability over time.
  • Data privacy risk: Sensitive production data is replicated twice, increasing GDPR/CCPA compliance exposure.
Consider one Full Copy (UAT) + one Partial Copy (integration testing) as a more cost-effective alternative.

Testing

5
What is automated browser testing?
▼

Automated browser testing uses tools to programmatically control a web browser and simulate user interactions — clicks, form fills, navigation — then assert expected outcomes without human intervention.

  • Common tools: Selenium, Playwright, Cypress, WebdriverIO.
  • In Salesforce: tests cover Lightning UI flows, Visualforce pages, and Experience Cloud sites.
  • Tests run in CI pipelines against sandboxes or scratch orgs.
  • Catches regressions that Apex unit tests cannot — UI rendering, LWC component behavior, page layouts.
LWC's Shadow DOM can make element selection tricky — use data-id attributes or Salesforce-specific selectors rather than CSS class names which may change between releases.
TestingUI
9
Static code analysis
▼

Static code analysis inspects source code without executing it to find bugs, security vulnerabilities, code smells, and style violations.

  • Salesforce tools: PMD (Apex ruleset), Salesforce Code Analyzer (wraps PMD, ESLint, RetireJS), Checkmarx.
  • What it catches: SOQL in loops, hardcoded IDs, missing sharing declarations, unused variables, potential null dereferences.
  • When to run: In CI pipelines on every PR/commit — fail the build if violations exceed a threshold.
  • Configured via XML rule sets; teams can disable or tune severity of specific rules.
TestingCode Quality
28
Negative unit testing
▼

Negative unit testing verifies that code behaves correctly when given invalid, unexpected, or out-of-bounds inputs — testing what should not work.

  • Ensures proper error handling and exception throwing rather than silent failures.
  • Examples: passing null where a record is expected, providing an invalid ID, exceeding governor limits intentionally.
  • In Apex: use try/catch inside tests and assert that the expected exception was thrown.
  • Validates that custom error messages surface correctly to users.
Pattern: set a boolean exceptionThrown = false before the try block, set it true in the catch block, then System.assert(exceptionThrown) after.
TestingApex
17
Difference between load performance and stress testing
▼
  • Load testing: Validates system behavior under expected production load. Confirms response times and throughput meet SLAs at normal/peak usage. The system is expected to remain stable and pass.
  • Stress testing: Pushes the system beyond its designed capacity to find the breaking point. Goal is to understand failure modes, degradation patterns, and recovery behavior — not to confirm it passes.

Source Control & Development Models

31
What is source control?
▼

Source control (version control) is a system that tracks changes to files over time, enabling teams to collaborate, review history, revert mistakes, and manage parallel lines of work.

  • In Salesforce: metadata (Apex, LWC, objects, flows) is stored as files in a Git repository rather than only living in an org.
  • Provides a single source of truth, enabling automated deployments and full audit trails.
  • Common platforms: GitHub, GitLab, Bitbucket, Azure DevOps.
GitDevOps
32
Difference between org development model and package development model
▼
  • Org Development Model: Changes are made in persistent orgs (sandboxes), retrieved to source control, and deployed to other orgs. The org is the system of record. Simpler to start, harder to enforce modularity.
  • Package Development Model: Metadata is organized into unlocked/managed packages built from source. Scratch orgs are the dev environment. Packages are the unit of deployment. Enforces modularity, versioning, and reproducibility.
SFDXArchitecture
16
Meaning of continuous integration
▼

Continuous Integration (CI) is the practice of frequently merging developer code changes into a shared branch, with each merge automatically triggering a build and test suite.

  • Detects integration bugs early — before they compound with other changes.
  • In Salesforce: each PR triggers a check-only deployment + Apex test run against a sandbox or scratch org.
  • Relies on automated tests being fast, reliable, and comprehensive enough to provide confidence.
  • CI is the foundation for Continuous Delivery (CD), which extends into automated production deployments.
CI/CDDevOps
19
What is a hotfix branch?
▼

A hotfix branch is a short-lived git branch created directly from the production release tag/branch to fix a critical bug, bypassing the normal feature development cycle.

  • Common naming: hotfix/<issue> or fix/<ticket-id>.
  • Branched from main or the production tag — not from the current development branch.
  • Once verified, merged back into both main and the current development branch to prevent the bug reappearing in the next release.
  • Keeps the hotfix isolated from in-progress feature work.
GitHotfix
20
What is a hotfix environment?
▼

A hotfix environment is a dedicated sandbox used exclusively for developing, testing, and validating emergency production fixes — kept separate from main development/UAT sandboxes.

  • Refreshed from production (or a recent snapshot) so metadata exactly matches what is live.
  • Used to reproduce the bug, develop the fix, and validate it before deploying directly to production.
  • Often paired with a dedicated hotfix CI pipeline that bypasses normal sprint gates.

Architecture

11
Circular relationships
▼

A circular relationship occurs when Object A references Object B and Object B (directly or transitively) references Object A, creating a cycle in the data model.

  • Salesforce prevents circular master-detail relationships at the platform level.
  • Circular lookup relationships are possible but introduce risk: trigger loop recursion, complex SOQL, and deployment ordering problems.
  • Mitigation: Redesign with junction objects, or break the cycle with a non-required lookup on one side.
Data ModelRisk
12
Depth of nested relationships
▼

Salesforce enforces a maximum depth of 5 levels for relationship traversal in SOQL:

  • SOQL supports traversal up to 5 levels of parent relationships in a single query (e.g., Contact.Account.Owner.Manager.Department).
  • Deep nesting increases query complexity, CPU time usage, and risks hitting SOQL row limits.
  • In the data model, deeply nested master-detail chains create tight coupling — ownership and sharing rules cascade all the way down.
  • Best practice: Keep relationship depth to 3 levels or fewer for maintainability.
Data ModelSOQL
13
DOM changes
▼

In the Salesforce context, DOM changes most commonly refer to LWC Shadow DOM behavior and Salesforce's periodic updates to component rendering.

  • LWC uses native Shadow DOM — child component internals are encapsulated and not accessible from parent JS or external CSS.
  • Salesforce has been migrating from synthetic shadow (polyfill) to native shadow — this can break browser tests and JS that queries into component internals.
  • Third-party test tools may fail when Salesforce updates DOM structure in a release (use preview sandboxes to catch these early).
LWCShadow DOM
14
Kanban board
▼

A Kanban board is a visual project management tool representing work items as cards moving through columns (To Do → In Progress → Review → Done).

  • Key principle: WIP limits — each column has a cap to prevent bottlenecks and surface flow problems.
  • Salesforce has a native Kanban view in List Views — switch via the display options toggle on any object list view.
  • Common external tools: Jira, Azure DevOps Boards, Trello, Linear.
AgileProject Management
15
Tooling API
▼

The Salesforce Tooling API provides programmatic access to metadata and development tools used by IDEs, CI systems, and code coverage dashboards.

  • Query Apex class metadata, code coverage data, debug logs, and compile/execute Apex anonymously.
  • Used by VS Code Salesforce Extension Pack for anonymous Apex execution and inline coverage overlays.
  • Supports SOQL-like queries on: ApexClass, ApexTrigger, ApexCodeCoverage, TraceFlag, etc.
  • Endpoint: /services/data/vXX.0/tooling/

Orgs & Editions

18
Difference between Developer Edition and Partner Developer Edition
▼
  • Developer Edition (DE): Free, 5 MB data / 20 MB file storage, 2 user licenses. Limited governor limit headroom. Available to anyone.
  • Partner Developer Edition (PDE): Available to Salesforce Partners via the Partner Community. 1 GB data / 1 GB file storage, 100+ user licenses, Enterprise Edition feature set, namespace support for managed packages, Trialforce access, LMA access.
PDE is the recommended org for ISV app development and managed package testing.
ISVOrg Types
27
Benefits of a Partner Development Org
▼
  • Access to Enterprise and Unlimited Edition features (advanced sharing, territory management, etc.).
  • High storage and user license counts for realistic testing scenarios.
  • Ability to create and test namespaced managed packages for AppExchange.
  • Access to Trialforce for creating templated trial orgs for prospects.
  • Access to LMA (License Management Application) for managing subscriber installs.
  • Environment Hub access to manage multiple orgs from a single console.

APIs

29
REST API tree request
▼

The REST API tree request (/sobjects/<Type>/tree/) creates multiple related records in a single call using a nested JSON tree structure.

  • Create parent and child records atomically (e.g., Account + Contacts in one request).
  • Maximum of 200 total records across all nodes per request.
  • All-or-nothing: if any record fails, the entire request rolls back.
  • Uses @referenceId on each node so child records can reference parents within the same request body.
REST APIBulk Insert
30
REST API composite request
▼

A composite request (/composite) bundles up to 25 subrequests into a single HTTP call, each subrequest being a full REST API call (GET, POST, PATCH, DELETE).

  • Reduces network round trips — especially valuable for high-latency mobile clients.
  • Subrequests can reference outputs of earlier subrequests using @{referenceId.field} syntax.
  • allOrNone: If true, all subrequests roll back on any failure. If false, each is independent.
  • More flexible than tree requests — mix different SObject types and HTTP methods freely.

Process & Governance

22
Requirement traceability matrix
▼

A Requirement Traceability Matrix (RTM) maps each business requirement to its design, development tasks, test cases, and defects — proving complete coverage end-to-end.

  • Typical columns: Requirement ID, Description, Design Reference, Test Case ID, Test Status, Defect ID.
  • Proves to stakeholders and auditors that every requirement has been tested.
  • Identifies orphaned test cases (tests with no requirement) and untested requirements.
  • Maintained throughout the project lifecycle — updated as requirements change.
