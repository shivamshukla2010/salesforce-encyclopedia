Certification Overview

What is the Claude Certified Architect – Foundations?

The Claude Certified Architect – Foundations is an Anthropic partner-only certification (Salesforce is an authorized partner) that validates a practitioner's ability to make informed architectural decisions when building production-grade applications with Claude. It tests knowledge across four core technologies: Claude Code, the Claude Agent SDK, the Claude API, and Model Context Protocol (MCP).

Questions are scenario-based — drawn from real-world use cases such as agentic customer support systems, multi-agent research pipelines, CI/CD integrations, developer productivity tools, and structured data extraction.

This certification is NTK (Need to Know) — distributed only through Anthropic partner channels. Exam guide version 0.1, last updated Feb 10 2025.

📋 Exam Format at a Glance

  • Question type: Multiple choice — 1 correct answer, 3 distractors
  • Pass score: 720 out of 1,000 (scaled score)
  • No penalty for guessing — always answer every question
  • Scenarios: 4 of 6 scenarios presented randomly per sitting
  • Target candidate: Solution architects with 6+ months hands-on Claude API / Agent SDK / Claude Code experience
The exam tests judgment about tradeoffs, not recall of syntax. Distractors are deliberately plausible — they represent what a partially-informed architect might choose.

Domain 1 — Agentic Architecture & Orchestration (27%)

Key Concepts — Must Know

  • Agentic loop: Send request → inspect stop_reason → if "tool_use" execute tool + append result + loop → if "end_turn" present response. Never parse natural language to decide loop termination.
  • Hub-and-spoke: Coordinator manages all subagent communication. Subagents have isolated context — they do NOT inherit coordinator history automatically.
  • Spawn parallel subagents by emitting multiple Task tool calls in a single coordinator response (not across separate turns).
  • Programmatic enforcement vs prompt guidance: For deterministic business rules (identity verification before financial operations), use hooks/prerequisite gates. Prompt instructions have a non-zero failure rate.
  • Hooks: PostToolUse intercepts tool results for normalization before the model processes them. Tool call interception hooks enforce compliance (block refunds over threshold).
  • Session management: --resume <name> to continue named sessions; fork_session for divergent exploration from a shared baseline.
  • Task decomposition: Prompt chaining for predictable sequential workflows; dynamic adaptive decomposition for open-ended investigation tasks.
The #1 rule: prompt-based enforcement is probabilistic. When you need guaranteed compliance (financial ops, identity verification), use programmatic prerequisites — not system prompt instructions.

Domain 2 — Tool Design & MCP Integration (18%)

Key Concepts — Must Know

  • Tool descriptions are how LLMs select tools. Minimal descriptions → unreliable selection. Include input formats, example queries, edge cases, and boundaries explaining when to use it vs similar tools.
  • Too many tools degrades performance. 18 tools instead of 4–5 increases decision complexity. Give each agent only the tools it needs for its role.
  • Structured error responses: Return errorCategory (transient / validation / permission), isRetryable boolean, and human-readable descriptions. Generic "Operation failed" prevents intelligent recovery.
  • MCP server scoping: Project-level (.mcp.json) for shared team tooling; user-level (~/.claude.json) for personal/experimental servers. Use ${ENV_VAR} expansion in .mcp.json for credentials.
  • tool_choice: "auto" may return text; "any" forces a tool call; forced {"type":"tool","name":"..."} calls a specific tool.
  • MCP resources expose content catalogs (issue summaries, doc hierarchies) to reduce exploratory tool calls.

Domain 3 — Claude Code Configuration & Workflows (20%)

Key Concepts — Must Know

  • CLAUDE.md hierarchy: ~/.claude/CLAUDE.md (user, not shared via version control) → project-level (.claude/CLAUDE.md or root CLAUDE.md) → directory-level subdirectory files.
  • .claude/rules/ — YAML frontmatter paths: glob patterns for conditional rule loading (e.g., paths: ["**/*.test.tsx"] applies only when editing test files). Preferred over subdirectory CLAUDE.md when conventions span multiple directories.
  • Commands: .claude/commands/ (project-scoped, version-controlled, shared) vs ~/.claude/commands/ (personal only).
  • Skills: .claude/skills/ with SKILL.md frontmatter. context: fork runs in isolated sub-agent context (prevents polluting main session). allowed-tools restricts tool access. argument-hint prompts for required params.
  • Plan mode vs direct execution: Plan mode for complex tasks with architectural implications (microservice restructuring, library migrations affecting 45+ files). Direct execution for well-understood single-file changes.
  • CI/CD: -p / --print flag for non-interactive mode. --output-format json + --json-schema for machine-parseable structured output. Use independent Claude instances to review generated code (not the same session that wrote it).
If a new team member isn't getting instructions — check whether the config is in ~/.claude/CLAUDE.md (user-level, not shared) instead of the project-level file.

Domain 4 — Prompt Engineering & Structured Output (20%)

Key Concepts — Must Know

  • tool_use with JSON schemas is the most reliable approach for structured output — eliminates JSON syntax errors, but does NOT prevent semantic errors (values in wrong fields, totals that don't sum).
  • Nullable/optional fields prevent hallucination. When source documents may not contain a field, mark it optional — required fields force the model to fabricate values.
  • Few-shot examples > prose instructions for consistency. Provide 2–4 targeted examples for ambiguous scenarios demonstrating why one action was chosen over plausible alternatives.
  • Explicit criteria > confidence-based filtering. "Flag comments only when claimed behavior contradicts actual code" beats "be conservative" — general instructions fail to improve precision.
  • Message Batches API: 50% cost savings, up to 24-hour processing, no guaranteed latency SLA, no multi-turn tool calling. Use for overnight/weekly reports. Never for blocking pre-merge checks.
  • Retry with error feedback: On validation failure, send the original document + failed extraction + specific errors. Retries are useless when information is simply absent from the source.
  • Multi-pass reviews: Per-file local analysis + separate cross-file integration pass. Avoids attention dilution and contradictory findings from single large-context passes.
🧠

Domain 5 — Context Management & Reliability (15%)

Key Concepts — Must Know

  • "Lost in the middle" effect: Models reliably process information at the beginning and end of long inputs but may omit findings from middle sections. Place key summaries at the start, use explicit section headers.
  • Trim verbose tool outputs before they accumulate in context. 40+ field order lookups when only 5 fields are relevant wastes context budget.
  • Scratchpad files persist findings across context boundaries in extended sessions. Use /compact when context fills with verbose discovery output.
  • Escalation triggers: Customer explicitly requests a human; policy is ambiguous/silent; inability to make meaningful progress. NOT sentiment, NOT self-reported confidence scores.
  • Structured error propagation: Return failure type + attempted query + partial results + alternative approaches. Generic "search unavailable" hides context from the coordinator. Silently returning empty results as success is an anti-pattern.
  • Structured state persistence for crash recovery: Each agent exports state to a known location; coordinator loads a manifest on resume.
  • Claim-source mappings must be preserved through synthesis. Attribution is lost when summaries compress findings without preserving source URLs, document names, and page numbers.

Domain 1 — Agentic Architecture & Orchestration (27%)

What the exam tests: Your ability to choose between orchestration patterns, know when programmatic vs. prompt-based enforcement is required, and understand the mechanics of the agentic loop.

Core reading:

  • Claude Agent SDK overview — Understand AgentDefinition, allowedTools, Task tool, and hook lifecycle. Focus on how stop_reason drives the agentic loop.
  • Hooks reference — Learn PreToolUse, PostToolUse, tool interception, and SubagentStart/SubagentStop events. This session's settings.json is a real example: every tool call here goes through a PostToolUse telemetry hook.
  • Building agents guide — Study hub-and-spoke vs. peer-to-peer orchestration. The exam favors hub-and-spoke because it gives coordinators complete observability over the workflow.

Worked example — agentic loop in Python:

while True:
    response = client.messages.create(...)
    if response.stop_reason == "end_turn":
        break                           # done
    if response.stop_reason == "tool_use":
        tool_results = execute_tools(response.content)
        messages.append({"role":"assistant", "content": response.content})
        messages.append({"role":"user",      "content": tool_results})
        # loop back — never parse natural language to decide

Parallel subagents (single coordinator turn):

# ✅ Correct — one response, two Task calls = parallel execution
response.content = [
  {"type":"tool_use","name":"Task","input":{"description":"Research music sector ..."}},
  {"type":"tool_use","name":"Task","input":{"description":"Research film sector ..."}}
]

# ❌ Wrong — separate turns = sequential only
turn1: Task(music)
turn2: Task(film)
Exam trap: "The coordinator passes its full conversation history to each subagent." False. Subagents have isolated contexts. Pass relevant findings explicitly in the Task prompt.

Domain 2 — Tool Design & MCP Integration (18%)

What the exam tests: Tool description quality, MCP server scoping, error propagation patterns, and appropriate use of tool_choice.

Core reading:

  • Tool use documentation — Master the three tool_choice modes. Know that "any" forces a tool call but lets the model pick which one, while the object form forces a specific tool.
  • MCP specification — Focus on the isError flag pattern, resource catalogs, and the difference between project-scoped .mcp.json vs. user-scoped ~/.claude.json.
  • Tool design best practices — Study how description quality affects selection accuracy.

Tool description quality — before & after:

# ❌ Too minimal — model will guess incorrectly
{
  "name": "get_customer",
  "description": "Retrieves customer information"
}

# ✅ Rich description — enables reliable selection
{
  "name": "get_customer",
  "description": "Look up a customer record by email, phone, or customer ID.
    Use this FIRST before any order operations to verify identity.
    Input: { 'identifier': 'email | phone | customerId' }
    Example: { 'identifier': 'user@example.com' }
    Do NOT use for order lookups — use lookup_order for that."
}

Structured error response pattern (MCP):

# ✅ Gives coordinator enough context to recover intelligently
return {
  "isError": True,
  "content": [{
    "type": "text",
    "text": JSON.stringify({
      "errorCategory": "transient",     # transient | validation | permission
      "isRetryable": True,
      "attemptedQuery": "order #98765",
      "partialResults": [],
      "alternativeApproaches": ["retry in 30s", "check order via customer record"]
    })
  }]
}

# ❌ Hides context — coordinator can't make intelligent decisions
return {"status": "search unavailable"}

What the exam tests: CLAUDE.md hierarchy, glob-based rules, skill context modes, plan vs. direct execution triggers, and CI/CD flags.

Core reading:

CLAUDE.md hierarchy (who sees what):

~/.claude/CLAUDE.md          ← user-level: personal only, NOT in git
.claude/CLAUDE.md            ← project-level: version-controlled, shared ✅
  OR
CLAUDE.md (project root)     ← same as above
src/payments/CLAUDE.md       ← directory-level: applies when working in /payments

Rules with glob patterns — the right pattern for cross-directory conventions:

# .claude/rules/test-conventions.yaml
---
paths:
  - "**/*.test.tsx"
  - "**/*.spec.ts"
---
All test files must:
- Use React Testing Library (no Enzyme)
- Prefer userEvent over fireEvent
- Group assertions in logical it() blocks
- Mock at the module boundary, not inside components

Skill frontmatter — key fields:

# .claude/skills/security-audit.md
---
description: Run a security audit on a specified module
context: fork           # ← runs in isolated sub-agent, won't pollute main session
allowed-tools:
  - Read
  - Bash                # ← only these tools available; Write is blocked
argument-hint: "module path to audit (e.g. src/payments)"
---
Audit the specified module for OWASP Top 10 vulnerabilities...
Common exam distractor: "Put all shared conventions in a root CLAUDE.md and rely on Claude to infer which section applies." — This is unreliable. Use .claude/rules/ with glob patterns for conditional application.

Domain 4 — Prompt Engineering & Structured Output (20%)

What the exam tests: tool_use for structured output, nullable field strategy, few-shot examples, Message Batches API constraints, and multi-pass review design.

Core reading:

  • Structured output guide — Understand why tool_use with tool_choice: "any" eliminates syntax errors but not semantic ones. Know the nullable field pattern cold.
  • Message Batches API reference — Memorize: 50% cost, 24-hour window, no latency SLA, no multi-turn tool calling, custom_id for correlation.
  • Prompt engineering guide — Focus on few-shot example design and explicit criteria over general instructions.

Guaranteed structured output — the right setup:

tools = [{
  "name": "extract_invoice",
  "description": "Extract invoice fields from the document",
  "input_schema": {
    "type": "object",
    "properties": {
      "vendor_name":   {"type": "string"},
      "invoice_date":  {"type": "string", "description": "ISO 8601 format"},
      "line_items":    {"type": "array", "items": {"type": "object"}},
      "total_amount":  {"type": "number"},
      # ✅ Optional fields prevent hallucination when data is absent
      "po_number":     {"type": "string", "description": "null if not present"}
    },
    "required": ["vendor_name", "invoice_date", "line_items", "total_amount"]
    # po_number is intentionally NOT required
  }
}]

response = client.messages.create(
  ...,
  tools=tools,
  tool_choice={"type": "any"}   # ← forces a tool call; never returns plain text
)

Message Batches API — when to use it:

  • ✅ Overnight technical debt reports (latency doesn't matter, cost does)
  • ✅ Weekly log analysis across hundreds of files
  • ✅ Bulk document classification jobs
  • ❌ Pre-merge CI checks (blocks developers — needs real-time response)
  • ❌ Customer-facing chatbots (users expect <5s responses)
  • ❌ Any workflow requiring multi-turn tool calling within the batch

Domain 5 — Context Management & Reliability (15%)

What the exam tests: "Lost in the middle" mitigation, context trimming strategies, escalation trigger design, and crash-recovery state persistence.

Core reading:

  • Context window management — Study the "lost in the middle" effect empirically. Key mitigation: place the most important summary/instructions at the start AND end of the context, not in the middle.
  • Reliability patterns — Understand scratchpad files, /compact, and structured state persistence for long-running multi-agent workflows.

"Lost in the middle" mitigation pattern:

# ❌ Critical facts buried in the middle of a 200k-token context
system = """
[thousands of tokens of background context]
CRITICAL: Never approve refunds over $500 without supervisor approval.  ← may be missed
[thousands more tokens]
"""

# ✅ Critical rules at start AND reinforced at end
system = """
CRITICAL CONSTRAINTS (read first):
- Never approve refunds over $500 without supervisor approval
...
[background context]
...
REMINDER: Apply constraints listed at the top of this prompt.
"""

Escalation triggers — what the exam tests:

  • ✅ Customer explicitly requests a human agent
  • ✅ Situation falls outside defined policy scope (policy is silent)
  • ✅ Agent cannot make meaningful progress after reasonable attempts
  • ❌ Customer sounds frustrated (sentiment ≠ complexity)
  • ❌ Agent self-reports low confidence (LLM confidence scores are poorly calibrated)
  • ❌ Request involves a large dollar amount (amount alone doesn't require escalation)

Crash recovery with state persistence:

# Each subagent exports its state periodically
# research_agent.py
with open("state/research_manifest.json", "w") as f:
    json.dump({
        "completed_topics": completed,
        "partial_results": results_so_far,
        "pending_queries": remaining_queries,
        "last_checkpoint": datetime.now().isoformat()
    }, f)

# Coordinator loads manifest on resume
# claude --resume research-session-2026-05-17

Official Sample Questions (with Explanations)

Q1 Scenario 1 — Customer Support Resolution Agent D1 Agentic

Production data shows that in 12% of cases, your agent skips get_customer entirely and calls lookup_order using only the customer's stated name, occasionally leading to misidentified accounts and incorrect refunds. What change would most effectively address this reliability issue?

  • AAdd a programmatic prerequisite that blocks lookup_order and process_refund calls until get_customer has returned a verified customer ID.
  • BEnhance the system prompt to state that customer verification via get_customer is mandatory before any order operations.
  • CAdd few-shot examples showing the agent always calling get_customer first, even when customers volunteer order details.
  • DImplement a routing classifier that analyzes each request and enables only the subset of tools appropriate for that request type.
Why A: Programmatic enforcement provides deterministic guarantees that prompt-based approaches cannot. B and C rely on probabilistic LLM compliance — insufficient when errors have financial consequences. D addresses tool availability rather than tool ordering, which is not the actual problem.
Q2 Scenario 1 — Customer Support Resolution Agent D2 MCP

Production logs show the agent frequently calls get_customer when users ask about orders (e.g., "check my order #12345"), instead of calling lookup_order. Both tools have minimal descriptions ("Retrieves customer information" / "Retrieves order details") and accept similar identifier formats. What's the most effective first step?

  • AAdd few-shot examples to the system prompt demonstrating correct tool selection patterns, with 5–8 examples showing order-related queries routing to lookup_order.
  • BExpand each tool's description to include input formats it handles, example queries, edge cases, and boundaries explaining when to use it versus similar tools.
  • CImplement a routing layer that parses user input before each turn and pre-selects the appropriate tool based on detected keywords and identifier patterns.
  • DConsolidate both tools into a single lookup_entity tool that accepts any identifier and internally determines which backend to query.
Why B: Tool descriptions are the primary mechanism LLMs use for tool selection. When descriptions are minimal, models lack context to differentiate similar tools. B directly addresses this root cause with low effort. A adds token overhead without fixing the underlying issue. C is over-engineered and bypasses the LLM's natural language understanding. D is a valid choice but requires more effort than a "first step" warrants.
Q3 Scenario 1 — Customer Support Resolution Agent D5 Reliability

Your agent achieves 55% first-contact resolution, well below the 80% target. Logs show it escalates straightforward cases (standard damage replacements with photo evidence) while attempting to autonomously handle complex situations requiring policy exceptions. What's the most effective way to improve escalation calibration?

  • AAdd explicit escalation criteria to your system prompt with few-shot examples demonstrating when to escalate versus resolve autonomously.
  • BHave the agent self-report a confidence score (1–10) before each response and automatically route requests to humans when confidence falls below a threshold.
  • CDeploy a separate classifier model trained on historical tickets to predict which requests need escalation before the main agent begins processing.
  • DImplement sentiment analysis to detect customer frustration levels and automatically escalate when negative sentiment exceeds a threshold.
Why A: Explicit criteria with few-shot examples directly addresses the root cause — unclear decision boundaries. B fails because LLM self-reported confidence is poorly calibrated. C is over-engineered when prompt optimization hasn't been tried. D solves a different problem — sentiment doesn't correlate with case complexity.
Q4 Scenario 2 — Code Generation with Claude Code D3 Claude Code

You want to create a custom /review slash command that runs your team's standard code review checklist. This command should be available to every developer when they clone or pull the repository. Where should you create this command file?

  • AIn the .claude/commands/ directory in the project repository.
  • BIn ~/.claude/commands/ in each developer's home directory.
  • CIn the CLAUDE.md file at the project root.
  • DIn a .claude/config.json file with a commands array.
Why A: Project-scoped custom slash commands in .claude/commands/ are version-controlled and available to all developers on clone. B is personal-only. C is for project instructions, not command definitions. D describes a configuration mechanism that doesn't exist in Claude Code.
Q5 Scenario 2 — Code Generation with Claude Code D3 Claude Code

You've been assigned to restructure the team's monolithic application into microservices. This will involve changes across dozens of files and requires decisions about service boundaries and module dependencies. Which approach should you take?

  • AEnter plan mode to explore the codebase, understand dependencies, and design an implementation approach before making changes.
  • BStart with direct execution and make changes incrementally, letting the implementation reveal the natural service boundaries.
  • CUse direct execution with comprehensive upfront instructions detailing exactly how each service should be structured.
  • DBegin in direct execution mode and only switch to plan mode if you encounter unexpected complexity during implementation.
Why A: Plan mode is designed for complex tasks with large-scale changes, multiple valid approaches, and architectural decisions. B risks costly rework when dependencies are discovered late. C assumes the right structure without exploring the code. D ignores that the complexity is already known upfront.
Q6 Scenario 2 — Code Generation with Claude Code D3 Claude Code

Test files are spread throughout the codebase alongside the code they test (e.g., Button.test.tsx next to Button.tsx). You want all tests to follow the same conventions regardless of location. What's the most maintainable way to ensure Claude automatically applies the correct conventions?

  • ACreate rule files in .claude/rules/ with YAML frontmatter specifying glob patterns to conditionally apply conventions based on file paths.
  • BConsolidate all conventions in the root CLAUDE.md file under headers for each area, relying on Claude to infer which section applies.
