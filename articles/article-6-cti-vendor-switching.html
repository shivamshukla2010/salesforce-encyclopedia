CTI Multi-Vendor Switching Architecture in Salesforce

Custom Metadata Apex LWC Open CTI Strategy Pattern Softphone Telephony

🏠

Overview

1
What are we building and what problem does it solve?
▼

Salesforce agents need to make phone calls directly from within Salesforce. These calls are handled by a CTI (Computer Telephony Integration) vendor — a third-party telephony service. You may have 2 or 3 such vendors and need to switch between them by clicking a button, without changing any code.

Think of it like a food delivery app. Your app (Salesforce) wants to deliver food (initiate a call). The CTI vendor is the delivery service (Uber Eats, DoorDash). You want to switch delivery services without changing how you order.

The architecture uses a single active vendor pointer stored in a Custom Metadata record. Every component in the system — Apex callouts, JS SDK calls, softphone routing — reads this pointer before acting. A button click flips the pointer. Everything else changes automatically.

Integration Options

2
Option 1 — Server-Side Initiation with Telephony Disposition
▼

In this flow, Salesforce initiates the call server-side by sending only the Lead/Contact record ID to the CTI vendor. The vendor handles everything: fetching the phone number, placing the call, and then pushing a signal back to the Salesforce softphone adapter to auto-open the popup for the agent.

  • Salesforce Apex sends recordId → CTI vendor API
  • Vendor fetches phone number from its own system
  • Vendor initiates the outbound call
  • Vendor fires a disposition/webhook back to the softphone adapter
  • Softphone popup opens automatically for the agent
Key question to ask your vendor: Does your adapter support "auto-opening" the softphone via a server-side signal, without frontend initiation?
Vendor handles number lookup Fire-and-forget from Apex
3
Option 2 — API Call + Custom JS SDK Method (Claim the Call)
▼

In this flow, Salesforce hits the CTI vendor's API via Apex and receives a unique Call ID in the response. That Call ID is returned to the LWC component in the browser. The LWC then calls the vendor's JavaScript SDK method with that Call ID to "claim" the call and open the softphone layout.

  • Salesforce Apex fires HTTP request to CTI vendor API
  • Vendor responds with a unique callId
  • Apex returns callId to LWC
  • LWC calls window.VendorSDK.claimCall(callId)
  • Softphone opens; agent sees the active call
Key question: Does your vendor's Salesforce adapter expose a JavaScript SDK method that accepts a Call ID to open the softphone?
Salesforce controls the flow Call ID bridges Apex ↔ JS

The Active Vendor Pointer

4
What is the Active Vendor Pointer and why use Custom Metadata?
▼

Every part of the system must answer one runtime question: "Which CTI vendor is currently active?" The answer lives in a single Custom Metadata record with IsActive__c = true. All code reads this one record — there is no hardcoded vendor name anywhere.

A whiteboard in the call center says "Today we are using: Vendor 1." Every agent checks it before calling. To switch, you erase "Vendor 1" and write "Vendor 2." All agents automatically use the new vendor without any individual instructions.
Custom Metadata (CMDT)Custom Settings

Deployable via changeset?✅ Yes⚠️ Partial

Why CMDT was chosen: It travels with deployments (sandbox → production), so vendor config moves with your code and never needs to be manually recreated in each org.

The CMDT Record

5
What is a CMDT record? (Plain English)
▼

CMDT stands for Custom Metadata Type. A CMDT record is one row in a Custom Metadata Type — exactly like a row in a spreadsheet.

The Custom Metadata Type (CTI_Vendor_Config__mdt) is the spreadsheet. Each vendor (Vendor 1, Vendor 2, Vendor 3) is one row. Each column (endpoint, class name, active flag) is a field. Code reads from this spreadsheet at runtime to pick the right vendor.

The critical difference from a regular Salesforce record: CMDT records are part of your metadata layer, not your data layer. They deploy with your code via changesets and do not count against your storage limits.

Important: Writing to CMDT at runtime requires the Metadata API (Metadata.Operations.enqueueDeployment()), not a plain DML upsert. This is an asynchronous operation — the write is queued, not instant.

Apex Class Structure

8
Do we need separate Apex classes per vendor? What is the Strategy Pattern?
▼

You need one class per vendor for vendor-specific logic, plus three shared classes that never change. This is the Strategy Pattern — every vendor implements the same interface (ICTIVendor), so all callers are decoupled from vendor details.

ClassCountChanges when vendor switches?Changes when adding a 4th vendor?
ICTIVendor1✅ Never✅ Never
VendorXCTIService1 per vendor✅ Never — new class, old ones untouchedWrite one new class
CTIVendorFactory1✅ Never✅ Never
CallController1✅ Never✅ Never
ApexICTIVendor.cls
// The contract every vendor class must fulfill
public interface ICTIVendor {
    // Returns Call ID (Option 2) or null (Option 1)
    String initiateCall(Id recordId);
}
ApexCTIVendorFactory.cls
public class CTIVendorFactory {

    public static ICTIVendor getActive() {
        CTI_Vendor_Config__mdt cfg = [
            SELECT Adapter_Class__c
            FROM   CTI_Vendor_Config__mdt
            WHERE  IsActive__c = true
            LIMIT  1
        ];
        // Dynamically load the correct vendor class from CMDT
        Type t = Type.forName(cfg.Adapter_Class__c);
        return (ICTIVendor) t.newInstance();
    }

    public static CTI_Vendor_Config__mdt getConfig(String devName) {
        return [
            SELECT Named_Credential__c, API_Endpoint__c, HTTP_Method__c,
                   Call_ID_Response_Path__c, Timeout_ms__c
            FROM   CTI_Vendor_Config__mdt
            WHERE  DeveloperName = :devName
            LIMIT  1
        ];
    }
}
ApexVendor1CTIService.cls (example)
public class Vendor1CTIService implements ICTIVendor {

    public String initiateCall(Id recordId) {
        CTI_Vendor_Config__mdt cfg = CTIVendorFactory.getConfig('Vendor1');

        HttpRequest req = new HttpRequest();
        req.setEndpoint('callout:' + cfg.Named_Credential__c + cfg.API_Endpoint__c);
        req.setMethod(cfg.HTTP_Method__c);
        req.setTimeout(Integer.valueOf(cfg.Timeout_ms__c));
        req.setBody(JSON.serialize(new Map<String, Object>{
            'recordId' => recordId,
            'source'   => 'salesforce'
        }));

        HttpResponse res = new Http().send(req);
        Map<String, Object> body =
            (Map<String, Object>) JSON.deserializeUntyped(res.getBody());
        return (String) body.get('callId'); // Vendor 1-specific response key
    }
}
ApexCallController.cls
public class CallController {

    @AuraEnabled
    public static String startCall(Id recordId) {
        // This single line never changes regardless of which vendor is active
        return CTIVendorFactory.getActive().initiateCall(recordId);
    }
}

Full Call Initiation Flow

9
Step-by-step: what happens from button click to softphone opening?
▼
1
LWC Agent's browser
Agent clicks "Call" on a Lead or Contact record
LWC captures the click, extracts recordId from the page context, fires an Apex call to CallController.startCall(recordId).
2
Apex CallController.cls
Controller delegates to the factory
No vendor knowledge here — just CTIVendorFactory.getActive().initiateCall(recordId).
3
CMDT CTI_Vendor_Config__mdt
Factory queries the active CMDT record
SOQL: SELECT Adapter_Class__c FROM CTI_Vendor_Config__mdt WHERE IsActive__c = true LIMIT 1. Returns 'Vendor1CTIService'.
4
Apex CTIVendorFactory.cls
Factory dynamically loads the right class
Type.forName('Vendor1CTIService').newInstance() — no if/else, no hardcoding. The string came from the CMDT record.
5
Apex Vendor1CTIService.cls
Vendor class reads its own config and builds the HTTP request
Fetches its own CMDT row by DeveloperName. Builds the HttpRequest using Named_Credential__c, API_Endpoint__c, HTTP_Method__c.
6
API Vendor 1's servers
HTTP callout fires to Vendor 1's API
Vendor receives the request, initiates the call, returns JSON: {"callId": "abc-123-xyz", "status": "initiated"}.
7
LWC ← Apex
Call ID travels back to the browser
'abc-123-xyz' is returned through Vendor1CTIService → Factory → Controller → LWC Promise.
8
JS SDK window.Vendor1SDK
LWC calls the vendor's JavaScript SDK to claim the call
window[cfg.JS_SDK_Global__c][cfg.JS_SDK_Claim_Method__c]('abc-123-xyz') — equivalent to window.Vendor1SDK.claimCall('abc-123-xyz').
9
UI Softphone
Softphone opens — agent sees the call
Flow complete. If Vendor 2 were active instead, steps 3–6 would differ. Steps 1, 2, 7, 8, 9 are identical.

Single Softphone Layout Routing

10
How does one softphone layout route to the correct active vendor?
▼

Salesforce loads the softphone via a Call Center definition in Setup. The naive approach (one Call Center per vendor) would require an admin to manually reassign users every time you switch — impractical. The solution is a meta-adapter pattern: one permanent Call Center pointing to a single Visualforce page that loads all vendor SDKs and activates only the correct one by reading the CMDT record at page-load time.

Naive (1 Call Center per vendor)Meta-Adapter (recommended)
Call Center definitionsOne per vendorOne, permanent
User reassignment on switchRequired (admin action)Not required
Page reload needed after switchYesYes (reads CMDT at load time)
Setup changes on switchYesNone

The Call Center points to your meta-adapter VF page — set once, never touched again:

XMLCall Center definition
<CallCenter>
  <item sortOrder="0" name="reqAdapterUrl" label="CTI Adapter URL">
    /apex/CTIMetaAdapter
  </item>
</CallCenter>

The VF meta-adapter loads all SDKs and injects active vendor config:

VisualforceCTIMetaAdapter.page
<apex:page controller="CTIMetaAdapterController" showHeader="false">

  <!-- Load ALL vendor SDKs — only one will be activated -->
  <script src="{!$Resource.Vendor1SDK}"></script>
  <script src="{!$Resource.Vendor2SDK}"></script>
  <script src="{!$Resource.Vendor3SDK}"></script>

  <script>
    var ACTIVE_VENDOR = {
      sdkGlobal:   '{!activeVendor.JS_SDK_Global__c}',
      claimMethod: '{!activeVendor.JS_SDK_Claim_Method__c}',
      name:        '{!activeVendor.DeveloperName}'
    };
  </script>

  <script src="{!$Resource.CTIMetaAdapterJS}"></script>

</apex:page>

The meta-adapter JS wires Open CTI events to the active vendor's SDK:

JSCTIMetaAdapterJS.js (Static Resource)
var vendorSDK = window[ACTIVE_VENDOR.sdkGlobal]; // e.g. window['Vendor1SDK']

vendorSDK.init({
    onCallReceived: function(callData) {
        sforce.opencti.setSoftphonePanelVisibility({ visible: true });
        sforce.opencti.screenPop({
            type: sforce.opencti.SCREENPOP_TYPE.SOBJECT,
            params: { recordId: callData.linkedRecordId }
        });
    },
    onCallEnded: function() {
        sforce.opencti.setSoftphonePanelVisibility({ visible: false });
    }
});

// Expose a bridge so LWC can call it after receiving the Call ID
window.CTIBridge = {
    claimCall: function(callId) {
        vendorSDK[ACTIVE_VENDOR.claimMethod](callId);
    }
};
The softphone reads CMDT once at page load. After switching vendors, agents need to refresh their Salesforce page for the softphone to pick up the new vendor. If you need live switching without a page reload, use a Lightning Message Channel to signal the adapter to re-initialize — this is more complex but eliminates the refresh requirement.

The Vendor Switch Button — LWC

11
LWC component — HTML template and JavaScript controller
▼

This component shows all vendors as buttons, highlights the active one, and shows a loading spinner during the switch. It can be placed in the utility bar, a home page, or any Lightning app page.

LWC HTMLctiVendorSwitcher.html
<template>
  <div class="vendor-switcher">

    <div class="switcher-header">
      <h3>CTI Vendor</h3>
      <span>Active: <strong>{activeVendorLabel}</strong></span>
    </div>

    <template if:true={isSwitching}>
      <lightning-spinner alternative-text="Switching..." size="small"></lightning-spinner>
      <p>Switching to {targetVendorLabel}...</p>
    </template>

    <template if:false={isSwitching}>
      <div class="vendor-buttons">
        <template for:each={vendors} for:item="vendor">
          <button
            key={vendor.developerName}
            class={vendor.btnClass}
            data-name={vendor.developerName}
            data-label={vendor.label}
            onclick={handleVendorSwitch}
            disabled={vendor.isActive}>
            {vendor.label}
            <template if:true={vendor.isActive}>
              <span> ✓ ACTIVE</span>
            </template>
          </button>
        </template>
      </div>
    </template>

    <template if:true={errorMessage}>
      <div class="error-banner">{errorMessage}</div>
    </template>

  </div>
</template>
LWC JSctiVendorSwitcher.js
import { LightningElement, track } from 'lwc';
import getAllVendors    from '@salesforce/apex/CTIVendorSwitchController.getAllVendors';
import setActiveVendor from '@salesforce/apex/CTIVendorSwitchController.setActiveVendor';
import { ShowToastEvent } from 'lightning/platformShowToastEvent';

export default class CtiVendorSwitcher extends LightningElement {
    @track vendors = [];
    @track isSwitching = false;
    @track errorMessage = null;
    targetVendorLabel = '';

    connectedCallback() { this.loadVendors(); }

    loadVendors() {
        getAllVendors().then(result => {
            this.vendors = result.map(v => ({
                ...v,
                btnClass: v.IsActive__c ? 'vendor-btn active' : 'vendor-btn'
            }));
        }).catch(err => { this.errorMessage = err.body.message; });
    }

    handleVendorSwitch(event) {
        const name  = event.target.dataset.name;
        const label = event.target.dataset.label;
        this.isSwitching = true;
        this.targetVendorLabel = label;
        this.errorMessage = null;

        setActiveVendor({ vendorName: name })
            .then(() => {
                this.isSwitching = false;
                this.loadVendors();
                this.dispatchEvent(new ShowToastEvent({
                    title:   'Vendor Switched',
                    message: `Now using ${label}. Refresh to update the softphone.`,
                    variant: 'success'
                }));
            })
            .catch(err => {
                this.isSwitching = false;
                this.errorMessage = 'Switch failed: ' + err.body.message;
            });
    }

    get activeVendorLabel() {
        const active = this.vendors.find(v => v.IsActive__c);
        return active ? active.Label : 'None';
    }
}
12
Apex controller — getAllVendors() and setActiveVendor()
▼
ApexCTIVendorSwitchController.cls
public class CTIVendorSwitchController {

    // Returns all vendor records so the LWC can render buttons
    @AuraEnabled(cacheable=true)
    public static List<CTI_Vendor_Config__mdt> getAllVendors() {
        return [
            SELECT DeveloperName, Label, IsActive__c
            FROM   CTI_Vendor_Config__mdt
            ORDER BY Label ASC
        ];
    }

    // Called on button click — flips IsActive__c via the Metadata API
    @AuraEnabled
    public static void setActiveVendor(String vendorName) {
        Metadata.DeployContainer container = new Metadata.DeployContainer();

        for (CTI_Vendor_Config__mdt v : [
            SELECT DeveloperName, Label FROM CTI_Vendor_Config__mdt
        ]) {
            Metadata.CustomMetadata md = new Metadata.CustomMetadata();
            md.fullName = 'CTI_Vendor_Config.' + v.DeveloperName;
            md.label    = v.Label;

            Metadata.CustomMetadataValue field = new Metadata.CustomMetadataValue();
            field.field = 'IsActive__c';
            field.value = (v.DeveloperName == vendorName); // true for target, false for all others
            md.values.add(field);
            container.addMetadata(md);
        }

        // Async — completes in a few seconds, not instantly
        Metadata.Operations.enqueueDeployment(container, null);
    }
}
Async note: enqueueDeployment() queues the write — it does not complete instantly. The toast tells the agent the switch was requested. For production use, pass a callback class (second argument) to receive a Salesforce notification when the write succeeds or fails.

Summary & Key Rules

✓
Architecture summary — what changes vs what never changes
▼

The entire architecture reduces to one rule: every piece of vendor-specific knowledge lives in the CMDT record, not in code. Code only reads that record and routes accordingly.

What changes when vendor switchesWhat NEVER changes
Which CMDT record IsActive__c = trueLWC "Call" button component
Which Apex class Type.forName() loadsCallController.cls
Which API endpoint the HTTP callout hitsCTIVendorFactory.cls
Which JS SDK method is invoked in the browserICTIVendor interface
Which Named Credential is used for authCall Center definition + VF meta-adapter URL

Adding a 4th vendor = one new CMDT record + one new Apex class. Zero changes to existing code.
